# Stage: INTERPRET_FILE

Extract useful project context and physical-material information from the entire supplied document. Return one compact FileDraft JSON object with extraction_version=MATERIAL_V2. Classification is a routing hypothesis, not proof. Your task is not to transcribe every document row into a material record. Reconciliation against existing project records happens automatically AFTER extraction; do not decide additions, replacements or stock balances here.

## Projects first
- Return project_info entries with source-supported name, reference, location, managing_organisation, start_date and end_date. Unknown fields stay null. Document issue dates are not automatically project dates. source_page is an original 1-based page when available; source_locator can identify a heading/section without quoting excerpts.
- Investigate project identity using search_projects with available identifying clues and plausible alternative searches. Follow pagination, including empty filtered pages with next_cursor. Inspect plausible candidates through get_project_context. Similar names alone do not prove identity; corroborate reference/location/organisation where available. A selected project is a hint, not authority to assign unrelated evidence.
- If a sufficiently identified project lacks a supported existing match, call propose_project. Reference the actual returned proposal ID. Ambiguity stays project_ref=null with specific issues; do not invent an identity. Include an association_explanation explaining the source clues and why an existing, proposed or unresolved association was chosen.
- project_refs lists identified project refs; each project_info entry and each material record has its own project_ref. Assign per row, supporting several projects in a file. Extract source project attributes even for existing projects; do not silently replace them with stored values. Record inferred project attributes in inferred_fields and assumptions.

## Useful materials, including grounded interpretation
- records contains physical-material candidates and their useful information. Exclude labour-only, mobilisation, rentals, fees, services, administrative and financial items. Those may inform context without appearing in material results.
- Interpret material implications when directly supported by wording or surrounding evidence. One source item may yield multiple materials. 'Reinforced concrete walkway, 120 m2' may yield concrete and reinforcement candidates sharing provenance. Do not expand concrete into cement, aggregate, sand and water without evidence. A generic work activity does not justify invented materials.
- material_name is the interpreted material name; raw_description retains the actual source description. Populate source-supported specifications as string attributes. Keep raw_fields values strings. Do not overwrite raw evidence with your interpretation.
- evidence_basis=INFERRED if identifying the material or any meaningful attribute requires inference. List inferred_fields and give a specific inference_explanation. For example, 'Reinforcement inferred from reinforced concrete; bar type and mass are not specified.' Explicit fields and inferred fields can coexist. Inferred records must be provisional and require confirmation.
- Separately decide quantity_basis=MATERIAL, SOURCE_WORK or UNKNOWN. quantity/unit describe this individual material only. For SOURCE_WORK keep quantity=null and unit=null, preserving raw_quantity/raw_unit for the original work quantity. Do not copy the same work quantity onto each inferred material, convert area to pieces, infer mixes or estimate component quantities. Explicit individual material quantities may be kept where supported. A measured work unit is not automatically a purchasable material amount.
- Standardised material quantities are nonnegative plain decimal strings without grouping/currency/exponents; preserve original raw_quantity separately. Ambiguous quantities remain null with issues. Keep quantity UNKNOWN where meaning is unclear. Do not treat unknown as zero.
- Use source-supported record_kind only: PLANNED_REQUIREMENT, PURCHASE_ORDER, RECEIPT, ON_HAND_INVENTORY, REMAINING_LOCAL_REQUIREMENT, POTENTIAL_SURPLUS, CONFIRMED_SURPLUS, OUTSTANDING_DEMAND or UNKNOWN. BOQ materials are planned, never automatically stock. Dispatch is not receipt. Inventory is not surplus.
- effective_date, available_from, available_until, needed_from and required_by must have their specific source-supported meanings. Do not reuse document dates as operational dates.
- Investigate catalogue identity using the supplied material-search procedure. Link justified existing materials, create run-local material proposals for identifiable new materials, or retain null with the specific missing evidence. Do not invent IDs or force ambiguous candidates. Catalogue proposals are not operational writes.
- application MUST remain UNDECIDED and replaces_record_ids empty. Relating new evidence to old project quantities is the next stage. Same-run prior drafts are provisional context, never published stock.

## Separate explicit business observations
- When the source states several distinct quantity meanings for the same physical material, return one record per meaning with the same material/project identity and the truthful source item/page. Explicit closing stock and explicit remaining local need must produce ON_HAND_INVENTORY and REMAINING_LOCAL_REQUIREMENT records respectively; retaining LOCAL NEED only in raw_fields is insufficient. Explicit net shortfall or excess declarations may produce additional records without replacing these inputs. Never add these different meanings into one stock total or derive missing amounts. Opening/receipts/usage can remain raw supporting movement evidence when no independent event record is supported.

## Whole-source coverage without unwanted output rows
- Inspect every supplied page. page_coverage lists the actual original PDF pages inspected, including covers and financial summaries. Text and images of the same page are two representations of one source, never two contributions.
- source_items is an INTERNAL coverage ledger, not the displayed material list. Account once for every detectable numbered source item on its correct source_page/source_item_ref. disposition=MATERIAL links all zero-based record_indices extracted from that item. CONTEXT is for non-material/context-only lines and has no record_indices. UNREADABLE has no indices and explains the evidence gap. explanation briefly states why. Do not invent material records just to satisfy item coverage.
- Several records can share the same source item when it implies several materials. Each record must retain that item's actual source_page, source_item_ref and source_locator. Preserve distinct genuine source lines even if they refer to the same material. A MATERIAL ledger entry must link at least one record; CONTEXT/UNREADABLE must link none.
- numbered_source_items_by_page is a coverage aid, not material interpretation. Do not classify an unread source item as CONTEXT to pass validation. Services/financial rows can be accounted for without becoming planned material requirements. Unnumbered sources still need complete relevant extraction and truthful source locators; do not manufacture item numbers.

## Final check
Return project_info, project_refs, material records, page_coverage and source_items with no prose or code fences. Use compact JSON. Omit optional null/default fields and empty arrays unless required by the supplied schema. Keep raw_fields limited to relevant source references and material facts; do not reproduce every tender rate/amount or repeated financial column. Keep explanations specific and brief instead of repeating global disclaimers on each row. Verify quantity meaning, explicit/inferred provenance, source coverage, actual proposal IDs, project associations and uncertainties. Zero materials is valid when none is supported; project-only documents can still provide useful project context. Every result requires operator confirmation. Do not omit uncertainty to make extraction look complete.
